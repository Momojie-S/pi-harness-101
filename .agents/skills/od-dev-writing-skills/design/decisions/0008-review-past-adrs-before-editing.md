# 0008. 改 skill 前先复查过往 ADR(防撞号 / 重复 / 矛盾 / 重提已否)

- **Status**: accepted
- **Date**: 2026-08-07

## Context

硬规范 1 要求 `design/decisions/` 记 ADR(why),明说目的:**「后续修改者(人或智能体)知道当初为什么这么定,避免盲目改动破坏原意」**。但「创建/修改流程」**没有一步说「动手改 / 加 ADR 前先复查本 skill 的过往 ADR」**。后果(都属「修改错误」):

- **撞号**:加 ADR 未先查 INDEX,用了已占的编号。实测:同一仓库并行进程已写(未提交)某号 ADR,另一方未复查 INDEX 也写了同号 → 两份同号 ADR 文件冲突,要返工改名 + 改交叉引用。
- **重复已有决策**:把已经决策过的事再决策一遍(ADR 白写)。
- **改出和已有决策矛盾**:忽略已有 ADR 的约束 / 边界,改出新内容与旧决策打架。
- **重提已被否备选**:ADR 的 Considered Options 备选栏正是为「防后人重复扯皮同一个被否方案」;但不复查过往 ADR 就看不到被否项 → 把已否方案重新提一遍。

## Decision Drivers

- **ADR 是 immutable 决策记录,不复查 = 无视已有决策** —— 直接违反硬规范 1 立 ADR 的目的(「避免盲目改动破坏原意」)。立了 ADR 却不要求改前读它,ADR 就退化成只写不读的死档。
- **备选栏防重复扯皮的前提是「改前读它」** —— 不读,备选栏(ADR 最有价值的部分)就白写。
- **协作场景撞号是实实在在的事故**(多人 / 多进程同时改一个 skill 仓),非纯理论。

## Considered Options

1. **改前复查过往 ADR(本决策)**:动手改 / 加 ADR 前,读 INDEX + 相关 ADR。查三样:① 下一个编号(照 INDEX 接排,防撞);② 相关决策有无已覆盖(别重复 / 别矛盾);③ 相关被否备选(别重提)。
2. **不复查直接动手**:否 —— 撞号 / 重复 / 矛盾 / 重提已否,实测撞号已发生。
3. **复查方式:读 INDEX 定位 + 只读相关 ADR(选中)** vs 读全部 ADR:否 —— 全读成本高(大 skill ADR 多);INDEX + 按相关性精读足够定位三样。

## Decision

- **创建/修改流程第 1 步「定位」补「复查过往 ADR」**:编辑 / 加 ADR 前先读本 skill `design/decisions/`(INDEX + 相关 ADR),查 ① 编号 ② 已覆盖决策 ③ 被否备选。不复查就动手 = 撞号 / 重复 / 矛盾 / 重提已否。
- **第 4 步自检(review list)加一项**:「改 / 加 ADR 前复查过本 skill 过往 ADR 了吗(编号没撞 / 没重复已有决策 / 没改出矛盾 / 没重提已否备选)」。

**不进 SKILL.md 的**:复查的具体技巧展开(读 INDEX vs 全读的取舍)—— 判据级(读 INDEX + 相关)够,不展开。

## Consequences

- **正向**:少撞号(协作安全)/ 少重复决策 / 少改出矛盾 / 少重提已否备选(备选栏真正发挥作用)。
- **代价**:改前多读 INDEX + 相关 ADR(轻,INDEX 本就是为快速定位)。
- **推翻它会碎什么**:删复查 → 撞号 / 重复 / 矛盾 / 重提已否继续发生;ADR 备选栏白写(立了不读)。
