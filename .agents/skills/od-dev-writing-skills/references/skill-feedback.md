# skill 改进反馈:怎么写、写什么(给迭代方的输入规范)

> 本文件是 `od-dev-writing-skills` 的 situational reference。skill 在真实开发中会暴露 gap;本文件定义**反馈怎么写、写什么**,让后续迭代 skill 的方(子 agent 或人)能据反馈好好优化。
>
> **本文件只管反馈这个「输入」长啥样**。反馈的处理流程(谁改、干净上下文还是就地改、改哪、怎么验)**是各消费方 harness 的事**(取决于本地有没有 skill 源仓 / 挂载方式)—— 不在本文件规定。

## 为什么反馈要规范

迭代 skill 的方只能照反馈干活。反馈写得糊(没说清是通用 gap 还是模型怪癖、拟改是方法论还是具体例子)→ 迭代方要么 over-fit(把模型怪癖写进共享 skill)要么改错地方。故反馈要给足让迭代方做 **RCA 定夺 + 守规范** 的信息。

## 一条反馈该含什么

```
## [<skill名>] 观察:X 不够 / 缺 Y
- 为什么是通用 gap(RCA):...(判据见 writing-craft §3.1)
- 拟改(方法论级,非具体例子):...
- (若「卡住」类)卡在哪个任务(供验证重试):...
```

### 各字段要点

- **观察**:skill 哪里不够 / 缺什么,具体到 skill 哪节 / 哪个判据。别只说"不够好"。
- **RCA(为什么是通用 gap)** —— 迭代方做 RCA 定夺的关键输入:说清这 gap 是「任何合理模型/agent 按方法论走都会撞」(通用 → 可进 skill 正文),还是「只某模型怪癖 / 某环境失败」(特异 → 不进正文,进 design ADR)。判据见 `writing-craft.md` §3.1。**反馈只给 RCA 线索;严谨定夺由迭代方做**(写反馈别为套全套规范中断开发)。
- **拟改**:方法论级建议(怎么判断 / 怎么选),**非具体游戏例子**(规范4:具体例子归 doc/design,不归 skill 正文)。给方向即可,迭代方按规范细化。
- **卡住任务**(若适用):若这 gap 是「把我卡住」触发的,记下卡在哪个具体任务 —— 消费方 harness 的验证步会重试它验效果。

## 写反馈的纪律

- **别中断开发**:开发中发现 gap,快速写反馈(抓信号),别停下来为写完美反馈打断深做 —— 迭代方会补严谨。
- **份量匹配**:实质性 / 真卡住的 gap 写完整反馈;鸡毛蒜皮(笔误)记一句即可。
- **反馈是输入,不是结论**:反馈给迭代方方向 + RCA 线索;最终 RCA 定夺 / 4 硬规范自检 / 改哪 / 怎么验,由**消费方的迭代流程**负责(各按自己 harness,如本地有 skill 源仓 → 改源仓;只有挂载 → 按挂载方的方式)。
